## Backend implementation and failures

The Rust recipe is `crates/md-sim-firmware/examples/build_esp_qemu_backend.rs`. It reuses bounded QEMU build helpers and runs all acquired build programs in the existing isolated ProcessSpec environment. The toolchain consists of captured file bytes. It has no host `/usr` mount. Exact source, toolchain, overlay, recipe, patch and result identities are retained for each attempt.

- Attempt 001 reached Meson and failed because the captured GLib package required `sysprof-capture-4`. No build pass.
- Attempt 002 included transitive package providers. It reached target configuration but Meson omitted sysroot flags for build-machine compiler tests. No build pass.
- Attempt 003 put sysroot and `-B` in the compiler command itself. It reached the upstream floating-point test configuration and failed because Berkeley SoftFloat and TestFloat subprojects are absent. Those dependencies and their tests remain an open gate.
- Attempt 004 used a recorded diagnostic build patch. The patch adds an explicit option, default true, for generation of the unavailable upstream floating-point test executables. The diagnostic command sets it false. CPU and floating-point runtime implementations are unchanged. Configure passed. Compilation stopped at object 438 of 1419 because Espressif's network source includes `libslirp.h`; the captured package set lacked libslirp. No backend pass.
- Attempt 005 included libslirp. All 1,419 build steps passed. Export of the uncompressed binary exceeded the retained trace budget. The incomplete export remains a failure.
- Attempt 006 compressed the bounded binary export and verified both compressed and decompressed identities. Build, export and machine listing passed. The resulting QEMU hash is `ecd90c957f78ebb7e381714940a8d605694d50a3a27994229b99210d4283596b`, size 17,723,048 bytes. The original S3 ROM hash is `b5c7090cc22efce51c1323cef31ca96fcd673a5b1d1b1017e219d393f2659913`, size 393,216 bytes. This is a compile result; the machine still fails initialization as described below.
- Attempt 007 adds the captured libgcrypt dependency and explicitly enables it. The exact archived `hw/misc/meson.build` compiles the S3 AES/RSA devices only with libgcrypt, while `hw/xtensa/esp32s3.c` creates them unconditionally. The prior `--without-default-features` configuration therefore built an unusable S3 machine. The original source is unchanged. Build 007 passed; its binary hash is `06fcecfaf7b20a25f148e530406e473e9ed89d363cf44eed5e8460364eb29e1a`, size 17,735,304 bytes.
- Each attempt has `spec.json`, exact input objects, stdout/stderr hashes, the captured build envelope, build diagnostics and an assessment with firmware and exact target gates false. The diagnostic patch is `simulator/backends/esp32/diagnostic-fp-tests.patch`. It is not a test exemption for release acceptance.

## Original factory probes

`crates/md-sim-firmware/examples/esp32_original_probe.rs` checks the original factory, backend and ROM hashes. It attaches private derived flash, disables the display, monitor and NIC, and captures real UART output. Complete board, mining and native dashboard gates remain false.

- Probe 001 stopped before ROM execution. QEMU tried to allocate a 1 GiB JIT cache against the 1 GiB process address-space limit.
- Probe 002 sets `-accel tcg,tb-size=64`. It reached S3 machine construction, then failed with `unknown type 'misc.esp32s3.aes'`. No guest UART banner was produced. This led to the libgcrypt configuration fix above.
- Probe 003 constructed the machine and exited zero after 572 ms without any UART output. This is not firmware boot evidence. Its `-no-reboot` option was removed to permit the machine's real primary CPU reset path.
- Probe 004 captured real CPU reset diagnostics. They include ROM and application addresses, but no UART output. It ended with exit 137 near the configured CPU budget; the exact signal cause is not independently measured. Inspection found that the upstream UART discards bytes when the character backend is closed. The probe inherited `/dev/null` stdin, which can close QEMU's stdio backend immediately.
- Probe 005 keeps an empty private input pipe open inside the namespace while QEMU runs. It injects no guest bytes. Real logs show the archived ROM, ESP-IDF v5.5.3 bootloader and factory application load. Application startup aborts because the upstream PSRAM model defaults to quad mode. This proves the UART transport explanation without changing firmware or inventing console output.
- Probe 006 selects the existing `ssi_psram.is_octal=on` device property. It reaches actual octal PSRAM identification, the guest SPI SRAM memory test, multicore startup, and `esp-miner` v2.14.2 application information. The log stops after an eFuse calibration warning. The backend receives SIGKILL near its CPU budget; the exact signal cause is not measured. The log also retains failed oscillator and PSRAM timing calibration warnings. It is not a complete board boot. A private monitor diagnostic will identify the current CPU state without changing firmware or returning fabricated device values.

The exact frozen recipes, input objects, ProcessSpecs, results and raw logs are under `work/simulator/bitaxe/esp-qemu-build-*/` and `original-probe-*/`. Failed attempts remain intact.
